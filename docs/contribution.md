# 문석용의 triplan 개발 경험

> 단체 대화의 조건을 여행 선택지로 바꾸고, 친구들의 선택을 최종 일정까지 연결했습니다.

[프로젝트 소개로 돌아가기](../README.md)

## 담당 범위와 프로젝트 목표

2인 팀에서 서비스 기획과 주요 개발·통합을 주도하고, AI 프롬프트·발표·보고서 작성을 담당했습니다. 이 문서는 직접 구현·대응한 경험으로 확인한 AI 일정 생성, 장소 검증, 로그인·투표 흐름, 최종 일정 생성에 집중합니다. 역할은 본인의 개발 경험을 기준으로 기술하며, 커밋 수나 파일 수로 기여율을 산정하지 않습니다.

기업 과제의 AI 여행 플래너 요구사항을 바탕으로, 단톡방 대화 내보내기를 활용하는 방향을 제안했습니다. **여러 사람의 의견을 입력받고, 그 사람들이 최종 일정 형성에도 참여하게 하자**는 것이 기획의 중심이었습니다.

개발에는 AI 도구와 멘토 피드백을 활용했습니다. 제 역할은 기능의 목표를 정하고, 생성된 코드와 결과를 실제 흐름에서 확인하며, 의도와 다른 동작을 찾아 수정·통합하는 것이었습니다.

## 사례 1. AI가 만든 JSON을 실제 여행 일정으로 연결하기

### 문제

처음에는 짧게 구성한 대화에서도 조건을 제대로 추출하지 못하거나 일정 생성이 실패했습니다. A/B안이 비슷하게 나오고, 단순 희망이 필수 조건으로 해석되거나 1인 예산이 전체 인원 예산과 혼동되기도 했습니다. 장소 이름이 나와도 지도에는 다른 지역이 표시되는 문제가 있었습니다.

### 선택과 구현

멘토에게 역할 분리를 제안받아 조건 파싱과 일정 생성을 나눴습니다. A안이 완성된 뒤 그 장소 목록을 B안에 전달해 두 안이 서로의 결과를 모르는 문제를 줄였습니다. 숙소·이동은 공유할 수 있게 두었습니다.

| 처리 | 실제 코드 | 책임 |
|---|---|---|
| 조건 추출 | `PromptTemplates`, `OpenAiClient` | 대화·요청사항을 여행 조건 JSON으로 변환 |
| 조건 정리 | `ParserNormalizationService.normalize` | 필수·제외·선호 조건 등의 정규화 |
| A/B 생성 | `AiGenerationService.callPlannerWithValidation` | 일정 생성 및 규칙 검사 연결 |
| 오류 대응 | `PlannerValidationService`, `PlannerRepairService`, `PlannerFallbackService` | 검증, 결과 데이터 보정, 재요청, 대체 후보 구성 |
| 실제 장소 확인 | `PlaceValidationService.validate`, `DestinationGeoFence.allows` | 카카오 검색 결과와 목적지 범위 확인 |
| 최종 저장 | `AiGenerationService.saveCandidateAndPlaces` | 장소 대체·제외, 순서 정리, 예상 비용 재합산 |

파서 API 호출은 예외가 발생하면 최대 3회 시도합니다. 파싱 이후의 모든 의미 오류까지 이 재시도 함수가 해결하는 것은 아닙니다. A/B 플래너는 각 최대 2회 시도하며, 검증에서 실패하면 가능한 오류를 코드로 보정하고 다시 검사합니다. 여기서 보정하는 대상은 **프로그램 소스가 아니라 생성된 일정 데이터**입니다.

예산은 전체 여행 견적 대신 **항공권·KTX·숙박·렌트카 비용을 제외한 1인당 현장 예상 지출**로 범위를 맞췄습니다. 장소별 비용을 합산하고 한도를 검사해, 인원수 곱셈과 합계 불일치를 제어했습니다.

### 실패 후 다시 사용할 수 있도록

일정 생성 실패가 S2의 끝없는 대기로 이어지는 것도 중요한 문제였습니다. `PlanService.generateWithAI()`에서 생성 중 상태를 먼저 저장하고, 커밋 뒤 비동기 작업을 시작합니다. 작업 실패 후에는 별도 트랜잭션에서 미완성 후보·장소를 정리하고 `DRAFT`로 복구합니다.

이 처리는 사용자가 다시 생성을 요청할 수 있게 만드는 장치입니다. 성공한 파싱·A안 결과를 보존해 중간부터 재개하는 구조는 아닙니다. 또한 A/B 생성 서비스 자체에는 트랜잭션이 있으므로, 모든 외부 호출의 DB 연결 점유를 없앴다고 설명하지 않습니다.

### 결과와 배운 점

조건 추출, 일정 생성, 장소 확인의 책임을 나눠 어느 단계에서 결과가 어긋나는지 확인할 수 있는 구조를 구현했습니다. 지역별 입력과 검증·보정 테스트를 통해 변경 영향을 확인할 기반도 마련했습니다.

실패 대응을 추가한다고 모든 입력의 품질이 보장되지는 않았습니다. 특히 실제 긴 대화에서는 제약 누락과 상충 의견 처리가 어려웠고, 준비된 지역별 대체 후보는 다양성을 제한했습니다. 다음 개선은 무조건 호출 단계를 늘리는 것보다 **실패 입력의 어느 단계에서 정보가 손실되는지 확인하고, 제약을 보존하는 전처리·평가를 마련하는 것**입니다.

## 사례 2. 먼저 경험하고 로그인하도록, 선택은 잃지 않도록

### 문제

처음 방문한 사용자에게 결과를 보여주기 전에 로그인을 요구하면 서비스의 가치를 느끼기도 전에 이탈할 수 있다고 생각했습니다. 호스트는 생성 결과를 본 뒤 공유할 때, 게스트는 일정을 보고 선택한 뒤 제출할 때 로그인하도록 흐름을 구성했습니다.

이 흐름에서는 로그인 페이지로 이동하거나 새로고침했을 때 선택이 사라지지 않아야 했습니다. 다시 제출하더라도 같은 사람의 투표가 새 표로 계속 늘어나서는 안 됐습니다.

### 선택과 구현

`S3VotePage`는 장소별 선택과 순서 선호를 여행 UUID별 `localStorage`에 보관합니다. 제출하려는 사용자가 비로그인이면 제출 대기 표시를 남기고, 로그인 복귀 후 저장된 선택을 `submitVotes()`로 전송합니다. 선택만 저장한 상태와 실제 제출 의사를 표시한 상태를 구분하기 위한 처리입니다.

`VoteService.saveBatch()`는 다음을 하나의 트랜잭션에서 처리합니다.

1. 플랜을 잠그고 `VOTING` 상태인지 확인합니다.
2. 로그인 사용자 또는 서버 게스트 경로의 투표자를 결정합니다.
3. 후보·장소가 해당 플랜에 속하는지 검사합니다.
4. 동일 사용자·장소의 기존 투표를 갱신하거나 새로 저장합니다.
5. 장소 점수와 순서 선호를 함께 반영합니다.

DB 스키마에는 `(user_id, place_id)` 유니크 키를 둡니다. SQL의 `ON DUPLICATE KEY UPDATE`를 직접 호출하는 방식이 아니라 기존 행 조회 후 갱신·삽입하는 구현입니다. 전체 일정 코멘트는 별도 요청으로 저장됩니다.

PC에서는 A/B와 지도를 함께 비교하고, 모바일에서는 선택한 후보에 집중하도록 `useIsMobile`과 `PlanViewLayout`에서 표시 구성을 나눴습니다.

### 결과와 배운 점

로그인 전 선택 → 로그인 이동 → 로그인 사용자로 제출하는 흐름과 재투표 갱신을 연결했습니다. 참여자 수와 장소별 투표 수를 구분해 대시보드에 표시했습니다.

로그인 전 임시 선택은 해당 브라우저에만 있습니다. 로그인 후 같은 계정으로 제출하면 동일 사용자로 처리하지만, 여러 기기에서 선택을 자동 동기화하는 기능이나 DB 게스트 데이터의 회원 병합 기능은 구현 범위에 포함되지 않습니다. 로그인 전환율 개선은 측정하지 않았습니다.

**근거 코드:** [S3VotePage](https://github.com/sku2026-triplan-dev/triplan-frontend/blob/V3.2/src/pages/S3VotePage.jsx) · [VoteService](https://github.com/sku2026-triplan-dev/triplan-backend/blob/V3.2/triplan/src/main/java/com/triplan/triplan/service/VoteService.java) · [PlanViewLayout](https://github.com/sku2026-triplan-dev/triplan-frontend/blob/V3.2/src/components/PlanViewLayout.jsx)

## 사례 3. A/B 중 하나를 고르는 결과에서, 장소를 재구성하는 결과로

### 문제

장소별 투표를 수집한 이유는 A안의 좋은 장소와 B안의 좋은 장소를 조합하기 위해서였습니다. 그러나 개발 중 최종 결과를 확인했을 때 점수가 높은 후보안 하나를 통째로 선택하는 동작을 발견했습니다. 동작하는 코드와 의도에 맞는 기능은 다르다는 것을 실제 테스트에서 확인한 경험입니다.

### 선택과 구현

최종 일정 생성 역할을 별도로 두고, A/B 후보와 장소별 투표·의견을 입력합니다. `FinalPlanAiService`는 기존 장소의 `source_place_id`를 선택하도록 요청하고, 백엔드는 그 ID에 해당하는 장소 데이터를 복사합니다. AI가 새 장소명·좌표·비용을 만들어낼 필요를 줄인 구조입니다.

호스트는 참여 상황을 보고 최종 생성을 직접 요청합니다. 과반수 자동 확정 조건은 사용하지 않습니다. AI 결과를 사용할 수 없으면 장소별 투표를 활용하는 규칙 기반 대체 구성을 사용합니다.

```text
POST /plans/{uuid}/finalize
  → 준비 트랜잭션: 호스트·상태 검사, 후보·투표 조회
  → 트랜잭션 밖: AI에 최종 일정 재구성 요청
  → 저장 트랜잭션: 플랜 잠금·상태 재검사, D안 저장

GET /plans/{uuid}/final
  → 저장된 최종 일정 조회
```

최종 생성과 조회를 나눠 S5 화면을 다시 열 때 생성 요청을 반복하지 않도록 했습니다. 저장 시 이미 확정된 경우 기존 결과를 반환합니다. 다만 동시에 들어온 요청이 저장 전에 각각 AI를 호출할 가능성은 남아 있습니다.

표시 문구도 정리했습니다. 내부 장소 ID와 투표 버튼 이름을 최종 설명에 노출하지 않도록 프롬프트와 후처리를 적용하고, 사용자에게는 ‘투표 기반 추천 일정’으로 안내합니다.

### 결과와 배운 점

현재 최종 생성은 후보안 전체의 승자를 고르는 방식에서 **기존 A/B 장소를 선택해 일정을 재구성하는 방식**으로 바뀌었습니다. 결과가 반드시 A/B를 같은 비율로 포함한다는 뜻은 아닙니다. 중요한 것은 투표 단위와 최종 생성 단위를 장소로 맞춘 점입니다.

기능을 완성했다고 판단하기 전에, 사용자가 기대한 결과와 실제 출력이 일치하는지 확인해야 한다는 것을 배웠습니다.

## 범위 판단과 협업

팀 안에는 구현 경험을 넓히려는 관점과 시연의 자연스러운 흐름을 우선하는 관점의 차이가 있었습니다. 개발 참여와 기대 수준의 차이로 어려움을 느낀 시점에는 멘토에게 상황을 공유했습니다.

특히 짧고 조건이 명확한 입력도 안정화 중인 상황에서 약 6,800자의 실제 대화가 실패하면서, 어느 수준을 완성 목표로 볼지 고민했습니다. 저는 **목적지와 날짜가 어느 정도 정해진 대화 → 취향 차이를 반영한 A/B → 투표 → 최종 일정**이라는 범위를 설명했고, 멘토는 제한된 캡스톤 기간에서 발표와 수행 경험에 초점을 맞추도록 조언했습니다.

이 과정에서 정한 입력 범위와 품질 기대치를 팀이 명시적으로 공유해야 한다는 점을 배웠습니다. 모든 의견 차이가 해소됐다거나 이후 역할 재분담이 완료됐다고 주장하지 않습니다. 주요 개발·통합과 발표 준비를 이어가 배포·시연까지 마무리한 경험으로 정리합니다.

## 배포와 직접 확인한 결과

- 학교에서 지원한 KT Cloud에 배포하고 프로젝트 시연을 완료했습니다.
- 카카오 알림톡 도입 제약에 대응해 브라우저 Web Push를 사용했습니다.
- 개발 당시 PC·Android·iOS에서 일정 관련 Web Push 알림 수신을 직접 확인했습니다. 모든 브라우저·OS 버전의 호환성 시험을 뜻하지 않습니다.
- D-1 리마인더는 Scheduler와 발송 기록을 사용하는 코드로 구현되어 있습니다. 이메일 발송 코드는 있으나 실제 수신 검증 경험으로 포함하지 않습니다.

배포·수신 경험은 본인의 개발 당시 확인 내용입니다. 현재 KT Cloud 지원은 종료되었고, 이 문서 작성 과정에서 서버를 복구하거나 외부 API를 재실행하지 않았습니다.

## 검증 범위와 다음 개선
